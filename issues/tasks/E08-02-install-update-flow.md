# E08-02: スマホへのインストール・更新運用フロー
親: [E08: リリース・配布](../epics/E08-release-and-distribution.md)

## 概要
ビルドしたAPKをスマホに転送・インストールする一連の流れを確立する。

## 完了条件
新しいAPKができてから、実機で更新が反映されるまでの手順が
迷わず再現できる。

## 手順
[docs/development.md](../../docs/development.md) の「リリース」に書いた。

- 最初の1回: 鍵を作る → リリース鍵のSHA-1をCloud Consoleに登録 →
  **スマホのデバッグ版を消す**
- 毎回: `appVersion` を上げてCHANGELOGに書く → `assembleRelease` →
  `adb install -r`

## 設計の決定

### USBデバッグで入れるのを基本にする
`adb install -r` なら上書きで、スマホのデータ(キャッシュ・認可)が残る。
USBでつなげないときの代わりとして、DriveにAPKを上げてスマホで開く方法も書いた。

### APKを inbox に置かない
inboxはCSVの置き場で、置いたものは全部読もうとする。APKを置くと
「CSVではない」として失敗扱いになり、ログが残る。別の場所に置く。

### デバッグ版とリリース版は同じスマホに同居させない
デバッグ版だけパッケージ名を変える(`.debug`)と同居できるが、GoogleのAndroid
クライアントはパッケージ名で登録するので、もう1つ登録が要る。スマホに入れるのは
リリース版だけにして、デバッグはエミュレータで行う。最初の1回だけデバッグ版を消す。

## 検証 (2026-09-25)
- エミュレータで、デバッグ版の上にリリース版を入れると
  `INSTALL_FAILED_UPDATE_INCOMPATIBLE` で拒まれることを確かめた
  (手順の「デバッグ版を消す」が要る理由)
- 同じ署名のデバッグ版の上書き(`installDebug`、versionCode 1 → 10000)では
  エミュレータのデータ(148点)が残った

## 実機での検証 (2026-09-26)
版を2.0.0にし(v1→v2の区切り。E08-03)、docs/development.md の「リリース」の手順どおりに入れた。

- `assembleRelease` で versionName 2.0.0 / versionCode 20000、リリース鍵で署名されたAPKができた
  (`aapt2 dump badging` と `apksigner verify` で確認)
- スマホ(Android 17)にはこのアプリがまだ入っていなかったので、デバッグ版を消す手順は要らなかった
- `adb install -r` で入った。本人がアプリを開き、Googleの同意を済ませ「Driveと同期」を押すと、
  `失敗: 10:` にならずに同期できた(取り込み0件・失敗0件)。リリース鍵のSHA-1の登録(E00-06)が正しく効いている。
  キャッシュがDriveから作り直され、エミュレータと同じ系列が並んだ
- **同じAPKをもう一度 `install -r` で上書きし、同期を押さずに開くと、系列の6行と前回の同期の記録が残っていた**。
  「期限内なので同期しない」と出て、開いたときの判定(E02-04)も実機で動いた
- 1日1回の確認のアラーム(E05)がスマホに予約されていた

画面の確認は `uiautomator dump` の文字だけで行い、額は伏せた。リリース版はデバッグできないので、DBは覗いていない。

## 未検証のまま残したこと
- **版を上げての更新**(2.0.0 → 2.0.1 など)はまだ。同じ版の上書きでデータが残ることまでは確かめた。
  版を上げても同じ `install -r` なので、違いは versionCode の比較だけ
- **通知の許可が下りていない**(2026-09-26時点、`POST_NOTIFICATIONS` が未許可)。許可するまで、同期の催促や
  リマインダーの通知はスマホに出ない。アプリのトップに許可の案内が出ている
- Drive経由のインストール
