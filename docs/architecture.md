# 仕組みと、そう決めた理由

コードを読めば「何をしているか」は分かる。ここに書くのは
**「なぜそうしたか」**、特に後から見て不可解に見えそうな判断。

判断の拠り所である設計の大原則は [CLAUDE.md](../CLAUDE.md) にある。
ここはその原則から**何が導かれたか**を書く場所。

## 全体の流れ

```
Drive/inbox のCSV
      │
      ▼
 ┌─────────────┐
 │ InboxScanner │  取り込み済み記録と突き合わせる
 └─────────────┘
      │
      ▼
 ┌─────────────┐
 │  CsvIngest   │  落とす → 足切り → 文字コード判定 → 区切り文字判定 → 分解
 └─────────────┘
      │
      ▼
 ┌─────────────┐   ヘッダーが既知  ┌──────────────┐
 │ CsvAdapters  │ ───────────────→ │ 各アダプター   │
 └─────────────┘                   └──────────────┘
      │ 未知                              │
      ▼                                   │
 ┌─────────────┐                          │
 │FallbackParser│ 列の中身から推測          │
 └─────────────┘                          │
      │                                   │
      └───────────┬───────────────────────┘
                  ▼
          ParsedData(2種類)
          ・Transactions … いつ・いくら動いたか
          ・Metrics      … いつ・いくらだったか
                  │
      ┌───────────┼───────────┐
      ▼           ▼           ▼
   backup/     記録(Room)   processed/へ移動
   (JSON)                      │
      │                        ▼
      │             問題があれば logs/
      ▼
 ┌─────────────┐   + corrections/ + settings/
 │  CacheSync   │  Driveの中身からRoomを丸ごと作り直す
 └─────────────┘
```

`InboxSync` がinboxの一周を、`CacheSync` がキャッシュの作り直しを受け持つ。
キャッシュを差分でなく毎回作り直す理由は
[E02-03](../issues/tasks/E02-03-drive-to-cache-sync.md)。
`DriveSession` が認可・トークン切れ・オフラインを引き受けるので、
UIはこの流れを気にしなくていい。

## 「Driveが正」から導いたこと

### Roomは消えてもいい前提で作る
`fallbackToDestructiveMigration` を有効にしてある。マイグレーションを
慎重に書くより、作り直してDriveから入れ直すほうが速くて安全。

**唯一の例外が「どのファイルを取り込んだか」の記録**。これだけはDriveを
見ても分からないので永続化している。ただしこれも失われたら
もう一度取り込むだけで、重複検出が二重計上を防ぐ。

### folder IDはキャッシュしない
毎回Driveに問い合わせる。IDを持つと、Drive側でフォルダを移動・削除
されたときに古いIDを掴み続けて分かりにくく壊れる。
毎回引き直せば自己修復する。コストは起動ごとに数回のAPI呼び出しだけ。

### processedだけでは復元できないのでbackupを書く
processedにあるのは**銀行ごとにバラバラな元CSV**。そこから作り直すと
全部パースし直しになるうえ、**パーサーを直すと過去の結果が変わる**。

backupには正規化済みの形を置く。これがあって初めて
「Driveから再構築できる」が本当に成立する。

### 人が入力したものは消えたら戻らないので、Driveに置く
Driveのデータは作り直せるかどうかで2つに分かれる。

| 作り直せる | 作り直せない(人が入力した) |
|-----------|--------------------------|
| `backup/`(CSVを再取り込みすれば出る) | `corrections/`(数値の補正)、`settings/`(項目の定義 `items.json`、明細のカテゴリと予算 `categories.json`、基準価額の取り先と比べる基準 `funds.json`) |

Roomにだけ書いてよいものは無い。項目の定義もアプリで入力するが、
正はDriveの `settings/items.json` に置く。
詳細は [E02-01](../issues/tasks/E02-01-schema-design.md)。

### 朝の確認のために、settingsの一部を端末に控える
朝の確認(E05)は同期しないのでDriveを読めない。そこで使う人の決めたもの(カテゴリの予算、基準価額の取り先)は、
**キャッシュを作り直すたびに**(同期・画面からの保存のどちらでも)`CacheSync` の結果から SharedPreferences に書き写す
(`BudgetStore`・`FundLocalStore`)。正はあくまでDriveで、控えは失っても次の同期で戻る。
画面から保存するときは、Driveの今のファイルを読み直してから、そのものだけを変えて書く
(画面が古い内容を持ったまま、ほかの決まりを上書きしないように)。
ただし `funds.json` はDBの中身に関係しないので、画面から保存したときはキャッシュを作り直さず、
Driveに書けた内容をそのまま控えに書く(作り直しはbackupを全部落とし直すので、保存のたびに待たされる)。
詳細は [E07-29](../issues/tasks/E07-29-category-budgets.md)・[E05-09](../issues/tasks/E05-09-nav-alert.md)・[E05-17](../issues/tasks/E05-17-faster-fund-save.md)。

### 項目にしない系列は `#` で始める
資産推移の点(`metric_point`)には、一覧の項目にしない系列もある: 純資産の合算(`#純資産`。画面の中だけ)、
ファンドごとの評価額・取得額・単価(`#保有|区分|ファンド名|値の種類`。backupにも入る)。
CSVの列名は `#` で始まらないので取り違えず、キャッシュを作るとき `#` で始まる系列には項目を作らない。
テーブルを足さずに済み、backupに入るので「Driveから作り直せる」も保たれる。
詳細は [E01-17](../issues/tasks/E01-17-fund-cost-basis.md)。

### 導けるものは保存しない
backupとsettingsから毎回出せるものは、別に書いておかない。書いておくと、元(取り込み・カテゴリの決まり)を直したときに食い違う。
- 投資信託の売却(E01-19)は、保有商品一覧の `#保有` の系列を取り込みごとに比べて出す(売った値を別に持たない)
- 振り返り(前の月 E03-10・1年 E03-12)・固定費(E07-26)・カテゴリ別の支出(E07-25)は、明細から毎回数える

### 公開データは取り先だけを持ち、値は見るときに取る
投資信託の基準価額は投資信託協会の公開データ(ファンドごとのCSV)から取る(E05-09)。Driveに置くのは人が決めた取り先
(ISIN・協会コード。`settings/funds.json`。ファンドごとの比べる基準(E05-14)も同じ行)だけで、基準価額そのものは保存しない。いつでも取り直せるうえ、協会のCSVには
設定来の全部が入っているので、貯めなくても推移が最初から揃う(E05-11)。
- 端末に控えるのは、朝の確認で取った最新の1点と設定来の最高値の1点だけ(画面と通知の判定用。失ってもよい。最高値はE05-13)
- 推移(E05-11)・売り切ったファンドの売った値(E01-19)は行を開いたときに。設定来の最高値(E05-12)は朝の確認と「今すぐ基準価額を取る」で、最新の1点と同じCSVから出して控える(E05-13)。取り先はファンド名での検索(E05-10)で決められる
- 取れなければその日は飛ばす・画面に「取れなかった」と出す(古い値で知らせない)

通信するのは朝の確認のこの1つと、画面を開いたときだけ。朝の確認で通信する例外は本人が決めた([CLAUDE.md](../CLAUDE.md))。

### 補正は元データに書き込まない
`corrections/` に別レイヤーとして持ち、読むときに重ねる。
パーサーを直して再取り込みしても補正が生き残るのがこの形の利点。
元データは銀行が出したそのまま残るので、後から検証もできる。

### 記録してから移動する
逆にすると、移動成功後に記録が失敗したとき「processedにあるが記録は無い」
状態になり、次回inboxに無いので**二度と見つからず黙って消える**。

記録が先なら、移動が失敗しても inbox に残って見える。
壊れるなら見える側に倒す。

## パーサーまわり

### 銀行名ではなく列の顔ぶれでマッチさせる
アダプターを銀行名で切ると、同じ形式を吐く別の銀行が来るたびに
中身が同じアダプターが増える。必須列が揃っているかで判定すれば
同形式の他行はそのまま通る。

列の順番にも依存しない。ヘッダー名から位置を引くので、
並びが変わっても後ろに列が増えても壊れない。

見出しが1行目に無いCSV(証券口座の保有商品一覧。区分ごとの表が並ぶ)は、アダプターが
ファイル全体を見て判定・パースする(`matchesRows` / `parseRows`。[E01-15](../issues/tasks/E01-15-securities-holdings-csv.md))。
既定は1行目を見出しにするので、ふつうのアダプターは気にしなくてよい。

列名の行が無いCSV(カードの明細。1行目に氏名が入る)だけは、1行目の**形**で見分ける
([E01-14](../issues/tasks/E01-14-credit-card-csv.md))。列名で判定するアダプターより後に置く。
知らない形のCSVは、文字を出さずにセルの種類だけをログに出す(`CsvShape`)。
1行目が列名とは限らないので、1行目の文字もログに出さない。

### パース結果の型は2つ
| 型 | 意味 | 例 |
|----|------|-----|
| `ParsedData.Transactions` | いつ・いくら**動いた**か | 銀行の入出金明細 |
| `ParsedData.Metrics` | いつ・いくら**だった**か | 資産推移 |

同じ「CSVのパース結果」でも性格が違うので、取り違えないよう型で分ける。

### 文字コードはUTF-8を先に試す
UTF-8として**厳密に**デコードして、壊れたバイトが1つでもあればCP932。
UTF-8のマルチバイト列は規則が厳しいのでShift_JISが偶然通ることはほぼ無い。
逆順(先にCP932)にすると必ず通ってしまうので、この順序でないといけない。

### 区切り文字は「揃っているか」で選ぶ
出現回数で数えると、摘要にカンマが入るタブ区切りファイルでカンマを
誤選択する。各候補で実際に分解して列数が揃うものを選べばタブが勝つ。

### 検出用の数値判定は金額パーサーより厳しい
`FieldParsers.parseAmount` は既知の金額列向けにわざと緩く、
`ABC123`でも123を返す。これを列の推測に使うと何でも金額列に見えるので、
フォールバックでは別の厳しい正規表現を使う。

### 読めない行は落とさずスキップして数える
合計行・フッター・空行は普通に混ざる。1行のためにファイル全体を
捨てるのは割に合わない。理由付きで溜めて先へ進む。

### 異常値は通さない
金額は絶対値10兆円、年は1900〜2100まで。桁が飛んだ値は行ずれか
区切り文字の誤判定なので、通すより弾くほうが安全。

## 重複検出

行単位で見る。ファイル単位(md5)だと**期間が重なるCSV**を拾えない。
先月ぶんと今月ぶんで数日重なるのは普通に起きる。

| 対象 | キー | 衝突したら |
|------|------|-----------|
| 取引 | 日付・出金・入金・摘要 | 先勝ち |
| Metric | 項目・日付 | **後勝ち** |

取引は「起きた事実」なので最初に見たものを残す。Metricは時点の残高なので、
後から取り込んだファイルのほうが新しくて正しい。

取引のキーに**残高を含めない**のは、同じ取引でも取り込むCSVによって
残高の並びが違うことがあるため。

**既知の限界**: 同じ日に同じ額の取引が本当に2件あると1件に潰れる
(交通費など)。二重計上のほうが資産額を狂わせるので、
取りこぼす側を選んだ。気になればE03-04の手動補正で足す。

## 個人情報の扱い

読めなかったCSV行には口座番号と氏名が入る(実データで確認済み)。

| 出力先 | 生データ |
|--------|---------|
| logcat | デバッグビルドのみ |
| Drive の `logs/` | **書かない**。行番号と理由だけ |
| 端末の「前回の同期」(E03-05) | **書かない**。`logs/` と同じ中身 |
| リポジトリ | 置かない |

`logs`は元ファイルがprocessedにあるので、行番号で突き合わせれば足りる。
ログに中身を複製する必要は無い。

## 認可とオフライン

`DriveSession` が全部引き受ける。

- トークンは1時間程度で切れるので、**401なら1回黙って取り直す**。
  それでも駄目なときだけ同意画面に誘導する。
- **認可より先にネットワークを見る**。圏外だと`AuthorizationClient`が
  「同意が必要」を返すため、そのまま進むと開けもしない同意画面に
  誘導してしまう(実機で踏んだ)。
- ただしそれだけでは「繋がっている」を保証しないので、実リクエストの
  `isOffline`と二段構えにしてある。

アプリ側にOAuthクライアントIDは埋め込まない。Console側で
「パッケージ名 + 署名SHA-1」に紐づくAndroidクライアントIDを作れば
Play Servicesが署名を照合する。**リポジトリに秘密情報が入らない。**

## 目標の「現在」は割当額

同じ系列を2つ以上の目標で測っていると、一覧を読むとき(`ItemOverview.load`)に
系列の値を上の目標から順に割り当て、`currentYen` を割当額に置き換える
([E07-10](../issues/tasks/E07-10-envelope-allocation.md))。進捗・不足の通知・
取り崩し・積み増しの月額・AI用の書き出しは、どれもこれを見るので個別の対応は要らない。

割当額は目標額で頭打ちになるので、「いつ目標を割るか」は系列 − 上の目標の分
(`availableYen`)で、「いつ届くか」は系列が上の目標の分 + 自分の目標額に届く日で数える。
目標の値を使う計算を足すときは、頭打ちで困らないかをここで確かめる。

## 明細の「使った額」の数え方は1つ

同じ月の支出が画面によって違う額にならないように、明細1行の使った額は `Summary.usedYen` だけで数える:
カードの利用明細は返品(入金として持つ)を引き、銀行のカード引き落としの行は数えない(内訳はカードの明細にある)。
積立投資の目安(E10-04)・カテゴリ別の支出(E07-25)・固定費(E07-26)・前の月の振り返り(E03-10)・1年の振り返り(E03-12)・
AI用の書き出し(E03-09)・純資産の見通し(E09-06)は、どれもこれを通す。平均に使う月は、どれも「今月と明細の無い月は使わない」考え方で選ぶ。
積立投資の目安・純資産の見通し・将来の評価額(E09-03)は `InvestPlan` の選び方を共有し、固定費とカテゴリ別の支出は
同じ考え方をそれぞれの中で書いている(見る月数が違うため)。
期間どうしを比べるとき(1年の振り返りの前の12か月との差)も、明細の無い月は0円と数えず、明細のある月の数を出す
(途中から取り込んだ年と比べて「増えた」と見せないように)。
カテゴリの無い明細は生活費として数える(多めに見積もる側。[E07-21](../issues/tasks/E07-21-transaction-categories.md))。

## 通知から画面を開く

通知(`NotificationRules.Notice`)に開く画面を持たせ(`screen`)、押すと `MainActivity` がextra(`open`)で受けて、
`AppRoot` が画面の積み重ねに足す。受け付ける画面は、前の月の振り返りと投資信託の損益だけ(知らない値は無視する)。
画面ごとに別のPendingIntentにする(同じrequestCodeだと、あとの通知のextraで上書きされる)。
通知の番号は鍵の最後の `:` より前から作るので、同じ種類の通知が別々に残るように鍵を決める
([E03-10](../issues/tasks/E03-10-monthly-review.md)・[E05-09](../issues/tasks/E05-09-nav-alert.md))。
