# E02-03: Drive取り込み結果→ローカルキャッシュ反映の同期処理
親: [E02: ローカルデータモデル・キャッシュ基盤](../epics/E02-local-cache-and-model.md)

## 概要
E01で取り込んだCSVのパース結果を、E02-02のRoom DBに書き込む処理。
corrections(E01-10)も合わせて反映する。

## 完了条件
CSV取り込みが成功すると、対応するMetric/Goalの値がローカルDBに
反映される。

## 作ったもの

同期ボタンを押したときの流れはこうなった。

1. フォルダを用意する(`settings/` を足して6つ)
2. inboxを一周する(E01のまま。backupにJSONを書く)
3. **`CacheSync.rebuild`**: `backup/` `corrections/` `settings/` を全部読み、
   Roomの3テーブルを1トランザクションで入れ替える

| クラス | 役割 |
|--------|------|
| `CacheSync` | 読んで(`rebuild`)、組み立てる(`build`、純粋関数) |
| `BackupReader` | `BackupWriter`が書いたJSONを読み戻す |
| `Settings` | `settings/items.json` の読み書き(形式は`Corrections`に揃えた) |

## 設計の決定

### 差分ではなく、同期のたびに丸ごと作り直す
E02-01で先送りにした判断。作り直しを選んだ。

- **Driveと食い違う状態が残らない。** 差分で入れていくと、補正を消した・
  項目を消した、を別に追いかける必要がある。作り直しならそのまま消える
- **取り込み済みの3ファイルが、processedを触らずに入る。** E01-09で
  backupに正規化済みの形が書いてあるので、そこから作れば済む。
  E01-07で「processedからinboxへ戻して読み直す」と書いていた手順は不要になった
- **入れ直し(E06-02)と同じ道を通る。** 「Driveから再構築できる」が、
  毎回の同期で実際に確かめられている

代償は、同期のたびにbackupを全部落とすこと。今は3ファイル、増えても
月に数件なので問題にならない。遅くなったらmodifiedTimeで変わったものだけ
落とす形にする。

### 作り直せないときは、今のキャッシュを残す
空や欠けたデータで入れ替えると、資産が消えたように見える。
以下のときは入れ替えずに理由を画面に出す。次の同期でやり直せばよい。

- backupの一覧が取れない
- backupのダウンロードが途中で失敗した(通信の問題なら次回は読める)
- correctionsかsettingsが読めない

このため `Corrections.load` を「読めなければ空」から「読めなければnull」に
変えた。空として扱うと、作り直したときに補正が黙って消える。

一方、**形が読めないbackupファイル**(版が違う、JSONが壊れている)は
そのファイルだけ飛ばして先へ進み、件数を報告に出す。1ファイルのために
全部を止めない(CLAUDE.mdの「落ちるよりスキップ」)。

### 重複の判定はE01-11の判断のまま
| | 衝突したら | 順序の根拠 |
|---|---|---|
| 取引 | 先に取り込んだほうを残す | backupをmodifiedTimeの古い順に読む |
| Metric | 後から取り込んだほうを採る | 同上 |

`build` の中で `LinkedHashMap` で重ねている。DBの制約(E02-02)でも
同じ結果になるが、落とした行数を報告に出したいのでここで数える。

`Deduplication.dedupeTransactions` / `dedupeMetrics` は使っていない。
あちらは元の型(`BankTransaction`)のリストを返すので、どのファイルから
来たか(`sourceFileId`)を持ち回れない。キーの作り方(`keyOf`)は共有している。

### 補正は由来を残して重ねる
`Corrections.apply` は値を置き換えるだけで、どれが補正かが分からなくなる。
画面(E03-04)で「手で直した点」を示せるように、`origin` を付けて重ねる。
「同じキーの補正は後勝ち」の判定は `Corrections.effective` に切り出して共有した。

### Metric項目の自動生成
E02-01のとおり、`settings` の項目に、まだ載っていないmetricKeyの
METRIC項目を足す。自動で足した分は `settings` に書かない。

## 検証 (2026-09-25)

**JVMユニットテスト(91件、うち追加12件)**
- `BackupReaderTest`: 書いたとおりに読み戻せる(0とnullの区別を含む)、
  知らない版は飛ばす、壊れた行だけ落とす
- `SettingsTest`: 3種類の往復、読めない項目だけ落とす
- `CacheSyncTest`: 取引の先勝ち、Metricの後勝ち、補正の由来、
  Metric項目の自動生成(settingsにあるものは足さない)

**エミュレータで実データ**: Driveの実物(backup 3ファイル)で同期した。

| | 結果 | E01-04の記録 |
|---|---|---|
| Metric | 148点(4系列×37点、2025-09-30〜2026-09-25) | 148点・4系列・同じ期間 |
| 明細 | 19件(2ファイルぶん、2026-08-02〜2026-09-25) | 14件 + 5件 |
| 項目 | 自動生成のMETRIC 4件 | − |
| origin | 全部 `CSV`(correctionsはまだ無い) | − |

- 初回の同期で `settings/` フォルダが作られた
- **2回目の同期で同じ件数になり、フォルダも作り直されない**ことを確認
- processedのファイルには触っていない(backupから入った)

## 未検証のまま残したこと
- **キャッシュを残す側の分岐**(一覧が取れない、途中でダウンロードが
  失敗する、correctionsやsettingsが読めない)。`DriveApi` を差し替える
  仕組みが無く、テストでも実機でも起こせていない
- **correctionsとsettingsの実ファイルを読む経路**。どちらもDriveにまだ
  ファイルが無いので「無ければ空」しか通っていない。中身の解釈は
  ユニットテストで確認済み。書く側の画面はE03-04・E07-01
- backupが増えたときの同期時間。今は3ファイルで、inboxの確認を含めて
  約10秒だった
