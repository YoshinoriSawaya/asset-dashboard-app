# 仕組みと、そう決めた理由

コードを読めば「何をしているか」は分かる。ここに書くのは
**「なぜそうしたか」**、特に後から見て不可解に見えそうな判断。

判断の拠り所である設計の大原則は [CLAUDE.md](../CLAUDE.md) にある。
ここはその原則から**何が導かれたか**を書く場所。

## 全体の流れ

```
Drive/inbox のCSV
      │
      ▼
 ┌─────────────┐
 │ InboxScanner │  取り込み済み記録と突き合わせる
 └─────────────┘
      │
      ▼
 ┌─────────────┐
 │  CsvIngest   │  落とす → 足切り → 文字コード判定 → 区切り文字判定 → 分解
 └─────────────┘
      │
      ▼
 ┌─────────────┐   ヘッダーが既知  ┌──────────────┐
 │ CsvAdapters  │ ───────────────→ │ 各アダプター   │
 └─────────────┘                   └──────────────┘
      │ 未知                              │
      ▼                                   │
 ┌─────────────┐                          │
 │FallbackParser│ 列の中身から推測          │
 └─────────────┘                          │
      │                                   │
      └───────────┬───────────────────────┘
                  ▼
          ParsedData(2種類)
          ・Transactions … いつ・いくら動いたか
          ・Metrics      … いつ・いくらだったか
                  │
      ┌───────────┼───────────┐
      ▼           ▼           ▼
   backup/     記録(Room)   processed/へ移動
   (JSON)                      │
      │                        ▼
      │             問題があれば logs/
      ▼
 ┌─────────────┐   + corrections/ + settings/
 │  CacheSync   │  Driveの中身からRoomを丸ごと作り直す
 └─────────────┘
```

`InboxSync` がinboxの一周を、`CacheSync` がキャッシュの作り直しを受け持つ。
キャッシュを差分でなく毎回作り直す理由は
[E02-03](../issues/tasks/E02-03-drive-to-cache-sync.md)。
`DriveSession` が認可・トークン切れ・オフラインを引き受けるので、
UIはこの流れを気にしなくていい。

## 「Driveが正」から導いたこと

### Roomは消えてもいい前提で作る
`fallbackToDestructiveMigration` を有効にしてある。マイグレーションを
慎重に書くより、作り直してDriveから入れ直すほうが速くて安全。

**唯一の例外が「どのファイルを取り込んだか」の記録**。これだけはDriveを
見ても分からないので永続化している。ただしこれも失われたら
もう一度取り込むだけで、重複検出が二重計上を防ぐ。

### folder IDはキャッシュしない
毎回Driveに問い合わせる。IDを持つと、Drive側でフォルダを移動・削除
されたときに古いIDを掴み続けて分かりにくく壊れる。
毎回引き直せば自己修復する。コストは起動ごとに数回のAPI呼び出しだけ。

### processedだけでは復元できないのでbackupを書く
processedにあるのは**銀行ごとにバラバラな元CSV**。そこから作り直すと
全部パースし直しになるうえ、**パーサーを直すと過去の結果が変わる**。

backupには正規化済みの形を置く。これがあって初めて
「Driveから再構築できる」が本当に成立する。

### 人が入力したものは消えたら戻らないので、Driveに置く
Driveのデータは作り直せるかどうかで2つに分かれる。

| 作り直せる | 作り直せない(人が入力した) |
|-----------|--------------------------|
| `backup/`(CSVを再取り込みすれば出る) | `corrections/`(数値の補正)、`settings/`(Goal・Reminderなど項目の定義) |

Roomにだけ書いてよいものは無い。項目の定義もアプリで入力するが、
正はDriveの `settings/items.json` に置く。
詳細は [E02-01](../issues/tasks/E02-01-schema-design.md)。

### 補正は元データに書き込まない
`corrections/` に別レイヤーとして持ち、読むときに重ねる。
パーサーを直して再取り込みしても補正が生き残るのがこの形の利点。
元データは銀行が出したそのまま残るので、後から検証もできる。

### 記録してから移動する
逆にすると、移動成功後に記録が失敗したとき「processedにあるが記録は無い」
状態になり、次回inboxに無いので**二度と見つからず黙って消える**。

記録が先なら、移動が失敗しても inbox に残って見える。
壊れるなら見える側に倒す。

## パーサーまわり

### 銀行名ではなく列の顔ぶれでマッチさせる
アダプターを銀行名で切ると、同じ形式を吐く別の銀行が来るたびに
中身が同じアダプターが増える。必須列が揃っているかで判定すれば
同形式の他行はそのまま通る。

列の順番にも依存しない。ヘッダー名から位置を引くので、
並びが変わっても後ろに列が増えても壊れない。

### パース結果の型は2つ
| 型 | 意味 | 例 |
|----|------|-----|
| `ParsedData.Transactions` | いつ・いくら**動いた**か | 銀行の入出金明細 |
| `ParsedData.Metrics` | いつ・いくら**だった**か | 資産推移 |

同じ「CSVのパース結果」でも性格が違うので、取り違えないよう型で分ける。

### 文字コードはUTF-8を先に試す
UTF-8として**厳密に**デコードして、壊れたバイトが1つでもあればCP932。
UTF-8のマルチバイト列は規則が厳しいのでShift_JISが偶然通ることはほぼ無い。
逆順(先にCP932)にすると必ず通ってしまうので、この順序でないといけない。

### 区切り文字は「揃っているか」で選ぶ
出現回数で数えると、摘要にカンマが入るタブ区切りファイルでカンマを
誤選択する。各候補で実際に分解して列数が揃うものを選べばタブが勝つ。

### 検出用の数値判定は金額パーサーより厳しい
`FieldParsers.parseAmount` は既知の金額列向けにわざと緩く、
`ABC123`でも123を返す。これを列の推測に使うと何でも金額列に見えるので、
フォールバックでは別の厳しい正規表現を使う。

### 読めない行は落とさずスキップして数える
合計行・フッター・空行は普通に混ざる。1行のためにファイル全体を
捨てるのは割に合わない。理由付きで溜めて先へ進む。

### 異常値は通さない
金額は絶対値10兆円、年は1900〜2100まで。桁が飛んだ値は行ずれか
区切り文字の誤判定なので、通すより弾くほうが安全。

## 重複検出

行単位で見る。ファイル単位(md5)だと**期間が重なるCSV**を拾えない。
先月ぶんと今月ぶんで数日重なるのは普通に起きる。

| 対象 | キー | 衝突したら |
|------|------|-----------|
| 取引 | 日付・出金・入金・摘要 | 先勝ち |
| Metric | 項目・日付 | **後勝ち** |

取引は「起きた事実」なので最初に見たものを残す。Metricは時点の残高なので、
後から取り込んだファイルのほうが新しくて正しい。

取引のキーに**残高を含めない**のは、同じ取引でも取り込むCSVによって
残高の並びが違うことがあるため。

**既知の限界**: 同じ日に同じ額の取引が本当に2件あると1件に潰れる
(交通費など)。二重計上のほうが資産額を狂わせるので、
取りこぼす側を選んだ。気になればE03-04の手動補正で足す。

## 個人情報の扱い

読めなかったCSV行には口座番号と氏名が入る(実データで確認済み)。

| 出力先 | 生データ |
|--------|---------|
| logcat | デバッグビルドのみ |
| Drive の `logs/` | **書かない**。行番号と理由だけ |
| 端末の「前回の同期」(E03-05) | **書かない**。`logs/` と同じ中身 |
| リポジトリ | 置かない |

`logs`は元ファイルがprocessedにあるので、行番号で突き合わせれば足りる。
ログに中身を複製する必要は無い。

## 認可とオフライン

`DriveSession` が全部引き受ける。

- トークンは1時間程度で切れるので、**401なら1回黙って取り直す**。
  それでも駄目なときだけ同意画面に誘導する。
- **認可より先にネットワークを見る**。圏外だと`AuthorizationClient`が
  「同意が必要」を返すため、そのまま進むと開けもしない同意画面に
  誘導してしまう(実機で踏んだ)。
- ただしそれだけでは「繋がっている」を保証しないので、実リクエストの
  `isOffline`と二段構えにしてある。

アプリ側にOAuthクライアントIDは埋め込まない。Console側で
「パッケージ名 + 署名SHA-1」に紐づくAndroidクライアントIDを作れば
Play Servicesが署名を照合する。**リポジトリに秘密情報が入らない。**
