# E01-05: 汎用金額抽出パーサー
親: [E01: Google Drive連携基盤](../epics/E01-drive-integration.md)

## 概要
未知のヘッダーフォーマットでも、数値っぽい列を正規表現で検出し、
金額情報だけでも抽出できるフォールバック処理を実装する。

## 完了条件
未登録フォーマットのCSVでも、エラーで止まらず金額データだけは
取り込める。

## 設計の決定

### ヘッダー名ではなく「列の中身」を見る
未知の形式なので列名は当てにならない(`きんがく`かもしれないし
英語かもしれない)。各列について「日付として読める値の割合」
「金額らしい値の割合」を数え、6割を超えた列をその種類とみなす。

### 検出用の数値判定は、既存の金額パーサーより厳しくする
`FieldParsers.parseAmount` は既知の金額列向けにわざと緩くしてあり、
`ABC123` でも 123 を返す。これを列の推測に使うと**何でも金額列に
見えてしまう**ので、検出には `^[-−△▲+]?[¥￥]?[\d,]+\s*円?$` という
別の厳しい判定を使う。口座番号のような英数字混じりの列を弾くため。

### 迷ったら「余分に拾う」ほうに倒す
推測なので取りこぼしも誤検出もある。未知の形式に対しては
「本命の列を落とす」より「関係ない数値列も拾う」ほうがマシ。
要らない系列は後から人間が見て捨てられる(E03-04の手動補正)。

その代わり、**推測で読んだことは画面に隠さず出す**(`(推測)` と表示)。
数字を鵜呑みにされるほうが困る。

### 日付の列が無ければファイルの更新時刻を使う
Metricには日付が要る。日付列が見つからないCSV(項目と金額だけの
縦持ちなど)では、Driveの `modifiedTime` を「このファイルの時点の値」
として使う。

### 結果はMetricとして返す
取引の意味(入金か出金か)までは推測できないので、
`ParsedData.Transactions` ではなく `ParsedData.Metrics` を返す。

## テストで見つかった不具合
`ParsedData.Metrics.latest()` が `maxByOrNull { it.date }` を使っていた。
**同着だと最初の要素を返す**ので、同じ日付の点が複数あると古い値が
残ってしまう。CSVは古い順に並ぶのが普通なので「同日なら後の行を採る」
に直した。日付列が無くて全点が同じ日付になるフォールバックで顕在化したが、
既知フォーマットでも同日に複数行あれば起きていた。

## 既知の限界
- **縦持ちのCSV**(`項目,金額` の2列で、行ごとに項目が変わる形)は
  1つの系列にまとまってしまう。「項目列がキーだ」とは推測できないため。
  同じ日付で衝突するので最新値は最後の行になる。
  実害が出たら専用アダプターを足すほうが早い。
- 連番や口座番号のような「金額ではない数値列」もMetricとして
  出てくることがある。上記の「余分に拾う」方針どおりで、仕様。
- ヘッダー行が無いCSV(1行目からデータ)は、1行目が列名として
  扱われて1行ぶん失われる。

## 検証結果 (2026-09-25)
実データを持っていないのでユニットテストのみ(全25件PASS)。
未知フォーマットのCSVを実際にinboxに置いての確認は未実施。

テストで確かめた挙動:

| 状況 | 期待 |
|------|------|
| 未知の列名 (`取引日,なんとか区分,きんがく,備考`) | 日付と金額を拾う |
| 日付の列が無い | ファイルの更新日を使う |
| 列名が空 | `列2` `列3` のように位置で呼ぶ |
| 英数字混じりの列 (`ABC123`) | 金額列と見なさない |
| 金額の列が1つも無い | 何も返さない(エラーにはしない) |
| 空のCSV | 落ちない |
| 列が欠けた行 | 落ちない、その行だけスキップ |
| マイナス・通貨記号つき | 拾う |

既存の3ファイルが誤ってフォールバックに回らないことも実機で再確認済み。
